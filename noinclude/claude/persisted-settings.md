# Persisted, cross-tab-synced reader settings (theme, font size, ...)

The reader UI is not an iframe — `content.js`'s `showReaderOverlay()` splices `reader.html` directly into each qualifying tab's own document, so every tab runs its own independent reader instance. A per-tab setting like theme or font size needs three things to work correctly everywhere: persist across reloads, apply on startup, and live-sync to every other open reader tab. `theme` and `fontSize` are both implemented this way today — use them as the template for any new user-configurable setting (e.g. line spacing, a reading-width preference, etc.):

1. **Storage:** persisted in `chrome.storage.local` under its own top-level key (not real `window.localStorage` — the reader runs in the page's own MAIN-world origin, which has no `chrome.*` access). From reader code, write via `saveObjectInLocalStorage(key, value)` and read via `getObjectFromLocalStorage(key)` ([extension/reader/LocalStorageManager.js](../../extension/reader/LocalStorageManager.js)) — these just `window.postMessage` to the content script; the actual `chrome.storage.local.get/set` calls happen in [extension/bridge.js](../../extension/bridge.js)'s `SAVE_OBJECT_IN_LOCAL_STORAGE`/`GET_OBJECT_FROM_LOCAL_STORAGE` handlers.
2. **Apply function, split in two:**
   - An absolute setter (e.g. `setTheme(value, shouldSave=false)` in [extension/reader/helpers.js](../../extension/reader/helpers.js), `setFontSize(value)` in [extension/reader/PopupDocumentManager.js](../../extension/reader/PopupDocumentManager.js)) that only applies the value to the DOM/state — this is what startup restore and incoming broadcasts call, and it must NEVER save.
   - The user-facing action (a keyboard shortcut in [extension/reader/KeyboardManager.js](../../extension/reader/KeyboardManager.js), a UI control, etc.) calls the setter and is the ONLY place that also calls `saveObjectInLocalStorage`. This asymmetry — only the user-initiated path ever writes to storage — is what makes broadcasting loop-safe by construction, not any equality check.
3. **Startup restore:** in [extension/reader/readerStartUp.js](../../extension/reader/readerStartUp.js), add a `useSaved<Setting>()` async function (mirroring `useSavedTheme`/`useSavedFontSize`), awaited from `loadUIAndIcons()` before `g.pdm.loadDocument()`/`loadCollage()` run. If the setter touches DOM elements that don't exist yet at that point in startup (e.g. `CurrentDocumentMainDiv`, only created inside `loadDocument()`), the restore function must just set the raw state property and let the later, already-existing apply-on-load call pick it up — do not call the DOM-touching setter directly at this stage (see how `useSavedFontSize` only sets `g.pdm.fontSize`, deferring DOM application to `loadDocument()`'s existing `applyFontSizeToPresentationDivs()` call).
4. **Cross-tab broadcast:** in [extension/bridge.js](../../extension/bridge.js), a single `chrome.storage.onChanged` listener (gated on `area === 'local'` and `isShowingReader`) checks `changes.<key>` and `window.postMessage`s a `<SETTING>_CHANGED` message into that tab's reader page — add a new `if (changes.<key>) {...}` branch alongside the existing `theme`/`fontSize` ones rather than a new listener. `chrome.storage.onChanged` fires in every tab's `bridge.js` instance (not just the one that wrote the change) — this is Chrome's native broadcast, so no `chrome.tabs.query`/`sendMessage` fan-out via `background.js` is needed.
5. **Receiving the broadcast:** in `readerStartUp.js`'s top-level `window.addEventListener("message", ...)` handler, add a `<SETTING>_CHANGED` branch that calls the absolute setter with `shouldSave`-equivalent left at its default (never true), guarded by comparing to the current in-memory value first to skip redundant DOM work in the tab that originated the change (that tab receives its own broadcast too, since Chrome doesn't distinguish the writer).
